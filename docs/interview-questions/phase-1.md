# Interview questions — Phase 1 (Java, domain modelling, PostgreSQL, testing)

These are questions this phase's code lets you answer from experience, not from memory.

## Java 21 / design

* **Why `record`s for the domain model?** Immutability, value semantics (`equals`/`hashCode`),
  compact constructors for invariants, exhaustive `switch` on sealed hierarchies. Show
  `GeoPoint` (validating compact constructor) and `OrderStatus.canTransitionTo` (state
  machine as data).
* **Why is `services/common` framework-free?** The same type is a DB row, a JSON body, and
  later an Avro record / Flink POJO. Zero deps ⇒ no version conflicts across the API and
  the Flink runtime, and the model can't accidentally depend on a web framework.
* **Where does validation live?** Structural invariants in the record (`GeoPoint` range,
  `OrderItem.quantity > 0`); *business* rules (legal status transitions) in the enum;
  request-shape validation (`@NotNull`, `@Positive`) at the API edge. `DriverLocation` is
  deliberately *not* validated on construction so bad GPS can still be parsed and sent to a
  DLQ.
* **`Clock` injection** — why? Deterministic time in tests (`OrderServiceTest` pins "now"),
  and a single seam for event-time later.

## PostgreSQL

* **Indexes you added and why:** `orders(status)` for the worklist query,
  `orders(created_at)` for time-range scans, `orders(customer_id)` FK lookups,
  partial unique `driver_shifts(driver_id) WHERE status='ACTIVE'` to enforce "one open
  shift per driver" in the database, GiST index on `geofences(geom)` for spatial containment.
* **Why `BIGINT GENERATED BY DEFAULT AS IDENTITY` over `serial`?** SQL-standard, no
  separate sequence-permission footgun, and `BY DEFAULT` still lets tests insert explicit
  ids. All PKs are stable surrogate keys ⇒ clean Kafka message keys for CDC.
* **Why `status` as `TEXT`, not a PG `enum` or `CHECK` list?** Adding a status becomes an
  application change, not a locking `ALTER TYPE` / constraint migration. The app enforces
  the allowed set via the state machine.
* **Optimistic locking:** `@Version` column ⇒ `UPDATE ... WHERE id=? AND version=?`; zero
  rows ⇒ `OptimisticLockingFailureException` ⇒ HTTP 409. No row locks held across the
  request.
* **OLTP vs OLAP:** why this database is Postgres and why driver-location analytics will
  *not* be (index bloat, vacuum pressure at 10k writes/s; columnar stores win for
  slice-and-dice). See [`architecture.md`](../../architecture/architecture.md).
* **PostGIS:** `geometry(Polygon,4326)`, `ST_MakeEnvelope`, GiST index, and later
  `ST_Contains(geofence.geom, ST_MakePoint(lon,lat))` for geofence detection on the write
  side (Flink does the same with JTS on the read side).

## Spring / data access

* **Spring Data JDBC vs JPA:** no lazy loading, no dirty-checking/flush surprises, SQL you
  can predict; works natively with immutable `record` aggregates. Trade-off: you model
  aggregate boundaries explicitly (here `OrderItem` is its own aggregate, *not* a
  `@MappedCollection`, so a status change never deletes/re-inserts items — which would
  churn PKs that CDC depends on).
* **Flyway:** schema is versioned migrations (`V1__init_schema`, `V2__seed_reference_data`),
  applied on startup, same artifact in tests and prod.

## Testing

* **Testcontainers:** integration tests run the real Flyway migrations against a real
  PostGIS container — the schema, the extension, and the ORM mapping are verified together,
  not mocked.
* **Singleton-container pattern:** one static container shared across all `*IT` classes so
  Spring reuses one application context; a per-class `@Container` would be recreated on a
  new port while the cached context still pointed at the old one.
* **Test pyramid:** fast domain unit tests (`common`), fast service tests with Mockito
  (`OrderServiceTest`), slower end-to-end HTTP tests over Testcontainers (`*IT`), split
  between Surefire (`test`) and Failsafe (`verify`).
